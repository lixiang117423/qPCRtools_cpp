# Contributing to qPCRtools

Thanks for considering a contribution. This document explains how to report a
problem, how to propose a change, what happens after you send it, and what you
can expect from the maintainer.

## Ways to contribute

**Report a bug or a wrong result.** Open an issue at
<https://github.com/lixiang117423/qPCRtools_cpp/issues> and include: the
version shown in the application (`Help → About`, or the release tag), your
operating system, the input data (or a minimal subset that still shows the
problem), what you expected, and what happened. If a number looks wrong,
please say which number and, if you have it, what R's `qPCRtools` package
returns for the same input — a mismatch between the two implementations is
treated as the highest-priority class of bug in this project.

**Ask an analysis question.** Please ask in an issue rather than by email, so
that the answer stays searchable for other users. Questions about which
quantification method or statistical test is appropriate for a given
experiment are welcome.

**Propose a change.** Open an issue first for anything larger than a small
fix, so that we agree on the approach before you spend time on it. Then send a
pull request that:

1. builds locally (`cmake -S code -B build`, `cmake --build build`, tests with
   `ctest --test-dir build`; see
   [`README.md`](README.md) and [`docs/04_windows_build.md`](docs/04_windows_build.md));
2. keeps the numerical core and the interface separate — analysis logic
   belongs in `code/src/Core/` (library `qpcr_core`), not in the Qt or JavaScript
   layers;
3. adds or updates unit tests in `code/tests/` for any change to numerical
   behaviour, using the fixtures generated by `code/tests/generate_reference.R`;
4. updates the relevant documentation and, when behaviour visible to users
   changes, `CHANGELOG.md`.

Continuous integration (`.github/workflows/ci.yml`) builds the project and
runs the test suite on every push and pull request. A pull request is merged
when the suite passes and the change has been reviewed.

## How decisions are made

The project is currently maintained by a single author (Xiang Li), who reviews
every contribution and is responsible for releases. Decisions are made in
public in the issue tracker; no separate governance body, contributor
agreement, or copyright assignment is required. Contributions are accepted
under the MIT license, the same license as the project.

Because numerical correctness is the point of this software, changes are
judged against one question first: does the result still agree with the
reference implementation? Where a change would alter results deliberately, say
so explicitly in the pull request, and explain which implementation is to be
treated as correct.

## Releases and support

Releases are tagged `vMAJOR.MINOR.PATCH` and published with pre-built Windows
and macOS binaries through GitHub Releases. Version numbers follow semantic
versioning: fixes that do not change results increment the patch number,
changes that add methods or options increment the minor number. Support is
provided on a best-effort basis through the issue tracker; there is no paid or
guaranteed support, and no service-level agreement.

## A note on AI assistance

Contributions developed with the help of generative AI tools are acceptable,
provided that (a) the contributor reviews, understands and verifies the code
they submit, and (b) the use of such tools is disclosed in the pull request
description. AI-generated changes that the submitter cannot explain or test
will be sent back.
